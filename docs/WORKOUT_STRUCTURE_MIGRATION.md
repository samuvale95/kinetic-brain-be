# Workout Structure Migration

## Overview

- `structure_json` for workouts now uses a rich, validated schema with explicit segments, steps, targets, and sport-specific zone constraints.
- The new schema is required for new plans generated by the AI and for manual workout creation.
- Returning data is validated via the new Pydantic models in `app/schemas/workout.py`, so any legacy payloads must be updated before exposing them to clients.

## JSON Schema Highlights

Each workout includes a `structure_json` object with:

- `sport`: canonical sport keyword (`run`, `bike`, `swim`, `triathlon`, …).
- `segments`: ordered list (e.g., `warmup`, `main`, `cooldown`) containing one or more `steps`.
- `steps`: either a single effort (`steady`, `interval`, `recovery`, `drill`, `strength`, `rest`) or a repeat block (`step_type: "repeat"`) containing nested steps.
- `duration`: `{ "type": "time"|"distance"|"repetitions", ... }` with required units per type.
- `target`: explicit guidance (`zone`, `heart_rate`, `power`, `pace`, `cadence`, `rpe`) with required numeric ranges; running/trail accepts `Z1–Z5`, cycling accepts `Z1–Z7`.
- `metadata`: optional focus, RPE target, description, and notes.

```json
{
  "sport": "run",
  "segments": [
    {
      "segment_type": "warmup",
      "name": "Warm-up",
      "steps": [
        {
          "step_type": "steady",
          "duration": {"type": "time", "seconds": 600},
          "target": {"type": "zone", "zone": "Z2"},
          "notes": "Easy jog"
        }
      ]
    },
    {
      "segment_type": "main",
      "name": "Intervals",
      "steps": [
        {
          "step_type": "repeat",
          "repeat": 6,
          "steps": [
            {
              "step_type": "interval",
              "duration": {"type": "time", "seconds": 120},
              "target": {"type": "zone", "zone": "Z4"},
              "notes": "Hard uphill effort"
            },
            {
              "step_type": "recovery",
              "duration": {"type": "time", "seconds": 120},
              "target": {"type": "zone", "zone": "Z2"},
              "notes": "Jog back down"
            }
          ]
        }
      ]
    },
    {
      "segment_type": "cooldown",
      "name": "Cool-down",
      "steps": [
        {
          "step_type": "steady",
          "duration": {"type": "time", "seconds": 600},
          "target": {"type": "zone", "zone": "Z1"},
          "notes": "Relaxed finish"
        }
      ]
    }
  ],
  "metadata": {
    "focus": "Base building with speed introduction",
    "rpe_target": 8,
    "description": "Maintain smooth form and breathing through the repeats."
  }
}
```

## Migrating Existing Records

1. **Identify legacy rows**
   ```sql
   SELECT id, structure_json
   FROM workouts
   WHERE structure_json ? 'description';
   ```

2. **Transform payloads**
   - Convert the legacy `{description, rpe_target, focus}` payloads into the new structure.
   - Suggested script (pseudo):
     1. Determine workout sport (`workouts.type` or `workout_plans.sport_type`).
     2. Build a structure with three segments (warm-up/main/cooldown).
     3. Place the legacy description into `metadata.description` and `steps[].notes`.
     4. Use workout `duration_minutes` to compute durations (`warmup = cooldown = 10 min`, remainder in the main block).
     5. Derive the target zone from `workouts.zone`; fall back to `Z2`.

3. **Validate**
   - Run the generated JSON through `WorkoutStructure(**payload)` (import from `app.schemas.workout`) before saving.
   - Keep a dry-run mode to spot validation errors without writing.

4. **Update rows**
   ```sql
   UPDATE workouts
   SET structure_json = :new_payload::jsonb,
       updated_at = NOW()
   WHERE id = :workout_id;
   ```

5. **Back up**
   - Export the original payloads (JSON dump) before overwriting to keep a rollback path.

## Testing Checklist

- ✅ Generate an AI plan (mock or live) and confirm the API returns `structure_json` with segments/steps.
- ✅ Fetch an existing plan: legacy workouts should now render using the new structure.
- ✅ Exercise both running (zones `Z1–Z5`) and cycling (zones `Z1–Z7`) cases to ensure validation works.
- ✅ QA fallback rendering in the frontend; ensure it can handle the nested structure.
- ✅ Review logs for `[WORKOUT_SERVICE] Invalid structured payload` warnings—these highlight payloads that still need manual attention.

## Rollout Notes

- The API will reject invalid structures at serialization time. Update/migrate legacy rows before exposing them to clients.
- The AI prompt now *requires* the structured payload. Monitor AI responses in `ai_response_logs` to verify compliance during the first runs.
- Keep the migration script handy for re-runs in case new legacy data surfaces (e.g., imported backups).
